# 发布、签名与自动更新

正式版本由 `v*` Git 标签触发 `.github/workflows/release.yml`，在 macOS、Windows、Linux 原生 Runner 上分别构建、执行测试、启动打包应用冒烟测试、生成 SHA-256 校验文件，并上传至同一个 GitHub Release。

## 发布密钥

仓库 Secrets 支持以下配置，证书与私钥不得提交到仓库：

- `MACOS_CERTIFICATE_BASE64`：Developer ID Application 的 P12 文件（Base64）
- `MACOS_CERTIFICATE_PASSWORD`：P12 密码
- `APPLE_API_KEY_BASE64`：App Store Connect API `.p8` 文件（Base64）
- `APPLE_API_KEY_ID`、`APPLE_API_ISSUER`：Apple 公证 API Key 标识
- `WINDOWS_CERTIFICATE_BASE64`：Authenticode PFX 文件（Base64）
- `WINDOWS_CERTIFICATE_PASSWORD`：PFX 密码

未提供证书时工作流仍可生成测试制品。macOS 测试包会在打包结束时对所有嵌套组件统一执行
ad-hoc 签名，以保证 Bundle 完整且可以在开发机启动；该签名不包含 Apple 信任链，也未经过
公证，因此不应作为面向最终用户的正式版本。正式分发和 macOS 自动更新必须使用
Developer ID Application 签名并完成 Apple 公证。

## 自动更新

标签构建会把 `${github.repository}` 固化为公开 GitHub 更新源。macOS 与 Windows 的正式包每 30 分钟检查一次更新；Linux 继续通过 DEB/RPM 包管理器升级。私有仓库或自建更新服务可在构建时设置 `JANUSGRAPH_UPDATE_BASE_URL`，使用静态更新源替代公开 Electron 更新服务。

发布前必须同步修改 `apps/desktop/package.json` 版本并创建同名标签，例如版本 `0.3.0` 对应标签 `v0.3.0`。工作流会拒绝不一致的标签。
